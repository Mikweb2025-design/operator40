## Le 7 modifiche, in ordine cronologico

### 1. `ce2bf14` — Angolo bilaterale visibility-aware con isteresi
**Problema:** 16 dei 22 analyzer calcolavano gli angoli bilaterali (ginocchio, gomito, linea tronco, flessione anca) come **media semplice sinistra+destra** `(al+ar)/2`, senza controllare la visibilità dei landmark. In side-view, il lato occluso ha comunque una stima (spesso sbagliata) da MediaPipe, e quella stima inquinava la media.

**Fix:** aggiunto `ExerciseAnalyzer.bilateralJointAngle(key, lm, left, right)` in [`src/ai/exercises/ExerciseAnalyzer.ts`](../src/ai/exercises/ExerciseAnalyzer.ts) — sceglie il lato più visibile invece di mediare sempre, con:
- **EMA sulla visibilità** (α 0.35) — smussa il rumore frame-per-frame
- **Isteresi sul cambio lato** (margine 0.12) — niente scatti quando la visibilità oscilla vicino alla soglia (0.4)
- **Hold sull'ultimo lato buono** se entrambi i lati scendono sotto soglia nello stesso frame

Applicato a: squat, pushup, affondo, crunch, deadBug, ginocchiaAlte, jumpingJack, legRaise, mountainClimber, plank, plankJack, ponte, sideplank, skater, superman, vUp, wallsit. **Non** applicato a esercizi dove sinistra≠destra è il segnale stesso (flutterKick, mountainClimber gamba guida, russianTwist, heelTap, bicycleCrunch).

### 2. `764bba7` — Non richiedere le caviglie per squat/affondo/wallsit/pushup
**Problema:** con la fotocamera frontale (FOV stretta), per far entrare tutto il corpo (incluse le caviglie) bisognava allontanarsi molto. `requiredLandmarks` includeva le caviglie, e `PoseQuality.evaluatePoseQuality` usa quella lista per decidere se mettere in pausa il tracciamento — piedi appena fuori dall'inquadratura → visibilità caviglie bassa → pausa.

**Fix:** rimosse le caviglie da `requiredLandmarks` in questi 4 esercizi (l'angolo le usa ancora quando sono visibili, si è tolto solo il *gate*).

### 3. `134cc49` — Causa reale del blocco in "idle" (badge su lista sbagliata + condizione invertita)
Due bug trovati leggendo `FitnessEngine.ts`/`SessionAIOverlay.tsx`/`FitnessEngineView.tsx`:
- Il **POSE%** mostrato in UI e il messaggio guida usavano sempre `def.requiredLandmarks` (lista generica, con caviglie), non la lista già ridotta dell'analyzer attivo → badge basso fuorviante anche quando il tracciamento funzionava.
- Il banner "Allontanati così vedo tutto il corpo" aveva la condizione **invertita**: `poseQuality < 42 && currentPhase !== 'idle'` — si nascondeva **esattamente** quando `currentPhase === 'idle'`, cioè nello stato in cui serviva di più.

**Fix:** `FitnessEngine.ts` ora usa `this.analyzer.requiredLandmarks` per il badge; rimossa la condizione `!== 'idle'` da entrambe le view. Rimosse le caviglie anche da `legRaise`/`deadBug`/`flutterKick`/`mountainClimber`/`vUp`/`ponte` (stesso motivo del punto 2, esercizi a terra).

### 6. `9f76c3a` — **IL BUG ROOT**: fase finale senza transizione d'uscita
Questo è il bug che ha causato "conta 0, la fase cambia ma la rep non scatta mai" — presente **da prima** di questa sessione, non introdotto oggi.

**Come l'ho trovato:** l'utente ha usato la funzione già presente nell'app `◯ REC landmarks` (in `FitnessEngineView.tsx`, pannello DEBUG) che registra i 33 landmark grezzi frame-per-frame in un JSON (via [`LandmarkRecorder.ts`](../src/ai/debug/LandmarkRecorder.ts)), senza video. Ho fatto il replay di quel JSON attraverso l'analyzer **fuori dall'app** (script Node/vitest temporaneo, non committato) e ho loggato ogni transizione di fase.

**Cosa mostrava il replay:** nei primi ~200ms, l'utente era vicino alla camera (hipY alto), il che faceva scattare l'OR-condition su hipY in `squat.ts` e produceva un ciclo completo `READY→DESCENDING→BOTTOM→ASCENDING→STANDING` **senza che il ginocchio si piegasse quasi per niente**. La rep non superava la soglia di confidenza (giusto, non era un vero squat) — ma da quel momento **`phase` restava bloccato su `STANDING` per il resto della sessione**, perché nessuna condizione di transizione in `squat.ts` gestiva `this.phase==='STANDING'` come stato di partenza. Il reset a `READY` (+ azzeramento di `trough`/`peak`) avveniva **solo** dentro il ramo "rep contata con successo", mai nel ramo "rep tentata ma non abbastanza sicura".

**Stesso identico schema in 7 analyzer:**
| Analyzer | Fase terminale senza uscita |
|---|---|
| `squat.ts` | STANDING |
| `pushup.ts` | TOP |
| `crunch.ts` | EXTENDED |
| `legRaise.ts` | DOWN |
| `vUp.ts` | EXTENDED |
| `ponte.ts` | DOWN |
| `affondo.ts` | STANDING |

`burpee.ts` aveva già un fallback a timeout per lo stesso rischio (introdotto in un giro di rifinitura precedente, commit `adeab6a`) — non era mai stato esteso agli altri 7.

**Fix (identico nei 7 file):** al termine di ogni ciclo completo, si torna **sempre** a `READY` e si azzerano `trough`/`peak`, indipendentemente dal fatto che la rep abbia superato o meno la soglia di confidenza. Pattern:
```ts
if (depthOk && extOk && repConf>62 && q.exerciseConfidence>38){
  if (this.shouldCountRep(ts,repConf,62)){ repInc=true; this.lastRepAt=ts; }
}
// Always cycle back to READY — STANDING has no other exit transition, so a single
// low-confidence attempt would otherwise lock tracking forever.
this.trough=ang; this.peak=ang; next='READY';
```

**Verifica:** stesso file JSON reale rieseguito → **0 rep prima del fix, 7 rep dopo**. Aggiunto test di regressione permanente in [`analyzers.test.ts`](../src/ai/exercises/analyzers.test.ts) ("a low-confidence squat attempt does not permanently lock the state machine") — simula un colpo a vuoto seguito da uno squat pulito, verifica che il secondo venga comunque contato.

### 7. `506cca4` — Calibrazione hipY per sessione (squat)
Con un **secondo** file di replay reale (8 squat puliti, stavolta contati correttamente grazie al fix precedente), si vedeva che **prima di iniziare a scendere** la fase sbatteva rapidamente READY↔DESCENDING↔BOTTOM↔ASCENDING decine di volte da fermo in piedi (non causava conteggi sbagliati, ma era rumore/instabilità visibile sull'HUD).

**Causa:** `hipY` a riposo dipende dalla distanza dalla camera. Con framing ravvicinato (anche favorito dal fix del punto 2), l'anca a riposo sta strutturalmente più in basso nel frame normalizzato (~0.65-0.70) della baseline fissa `0.55` assunta dal codice — le condizioni OR `hipY>0.58`/`hipY>0.62` scattavano di continuo senza movimento reale.

**Fix:** calibrazione per sessione — `restingHipY` si aggiorna via EMA (α 0.08) quando l'angolo ginocchio è >160° e la velocità è quasi nulla (persona ferma in piedi); le soglie diventano delta relativi a quella baseline (`hipYDelta>0.05`/`>0.09`) invece di costanti assolute. Nessuna soglia sull'angolo ginocchio toccata — resta la difesa primaria, hipY resta solo un helper OR.

**Verifica:** stesso replay → transizioni spurie da fermo azzerate (da decine a zero), 8/8 rep reali ancora contate correttamente (confidenza 100 su tutte).

## Come continuare a debuggare (il metodo che ha funzionato oggi)

Il salto di qualità nella sessione è arrivato quando si è passati da "guardare screen recording e ipotizzare" a **"replay di dati reali attraverso l'analyzer, fuori dall'app"**. Procedura:

1. Nell'app, schermata debug (`FitnessEngineView`, accesso: verificare come si raggiunge nell'app in produzione — nel test era raggiungibile scrollando la home), premere **`◯ REC landmarks`**, fare l'esercizio, premere di nuovo per fermare, poi **`↓ JSON`** per scaricare `landmarks-<esercizio>-<timestamp>.json`.
2. Scrivere un test vitest temporaneo (non committarlo) che:
   ```ts
   import { readFileSync } from 'node:fs';
   import { getAnalyzer } from './ExerciseRegistry';
   import { evaluatePoseQuality } from '../pose/PoseQuality';
   const raw = JSON.parse(readFileSync('/percorso/file.json', 'utf8'));
   const ana = getAnalyzer('<esercizio>')!;
   let lastT = raw.frames[0].t, reps = 0;
   for (const f of raw.frames) {
     if (!f.landmarks) { lastT = f.t; continue; } // alcuni frame sono null (nessuna persona rilevata)
     const dt = f.t - lastT || 16; lastT = f.t;
     const q = evaluatePoseQuality(f.landmarks, ana.requiredLandmarks);
     const r = ana.analyze(f.landmarks, f.t, dt, q);
     if (r.repIncrement) reps++;
     // loggare phase/repConfidence/exerciseConfidence per capire cosa succede
   }
   ```
3. `npx vitest run <file>` e leggere i log — si vede esattamente ogni transizione di fase, ogni valore di confidenza, molto più veloce che ipotizzare da screen recording.

## Pipeline di deploy (fonte di confusione oggi — leggere prima di rifarlo)

- **`main`** — sorgente. `git push origin main` basta per aggiornare GitHub.
- **`deploy-tmp`** — contiene `dist/` buildato, è il branch da cui il server live legge (via `raw.githubusercontent.com`). Va aggiornato **separatamente**: `git checkout deploy-tmp && git merge main && npm run build && git add -f dist && git commit -m "deploy: <hash>" && git push origin deploy-tmp -f`.
- **Server live (mikweb.eu)** — un **terzo passaggio**, via SSH, che scarica i file da `deploy-tmp` su `/var/www/vhosts/mikweb.eu/httpdocs/operator40/`. **Questa sessione non ha accesso SSH** — va fatto dall'utente o da un agente con quell'accesso. Verificabile lato client: `curl -s https://mikweb.eu/operator40/sw.js | grep "CACHE = "` deve mostrare la build attesa.
- **Attenzione:** esiste un processo automatico esterno (autore git `. <eet>`) che a volte fa merge/rebuild di `deploy-tmp` da solo — **non fidarsi ciecamente**: dopo ogni push, verificare sempre l'hash reale con `git fetch && git rev-parse origin/deploy-tmp` prima di dare istruzioni di sync, e verificare lato client con `curl` il valore di `CACHE` in `sw.js` dopo il sync, non solo assumere che sia andato a buon fine.

**Stato a fine sessione:** `main` e `deploy-tmp` entrambi a `506cca4`/`d21fbe2` (dist `o40-vabffcffe`) su GitHub. **Il server live non è stato ancora risincronizzato con quest'ultimo commit** — verificare con il curl sopra prima di assumere che sia aggiornato.
